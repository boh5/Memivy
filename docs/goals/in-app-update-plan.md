# Memivy 应用内更新实施计划

状态：基础实现已完成，代码与检查结果见 `DEVELOPMENT_PLAN.md`；真实正式包升级及 macOS 权限体验仍需隔离环境验收。

## 1. 目标与范围

为现有 Apple Silicon、macOS 26+ 应用增加最基础的应用内更新：

**检查更新 → 用户确认下载 → 校验更新包 → 用户确认安装 → 保存工作 → 安装并重启。**

采用 Tauri 官方 `tauri-plugin-updater`，复用 GitHub Releases 和现有发布流程。不增加服务器、账号或云端数据库。

本次实施范围也包括基础数据库版本检查、迁移前备份、顺序迁移、失败回滚，以及旧版备份恢复与迁移的衔接。不引入迁移框架或迁移管理界面。

## 2. 用户操作

- 在现有设置中显示当前应用版本和“检查更新”。第一版不做后台定时检查。
- 没有新版时显示“已是最新版本”；检查失败时显示可重试的错误，不影响普通使用。
- 发现新版时显示版本号、更新说明和“下载更新”。用户可以稍后再更新。
- 下载时显示进度；完成并校验通过后显示“重启并安装”。下载完成不代表已经安装。
- 只有用户确认后才进入安装流程。更新入口与状态使用现有界面组件，并提供中英文文案。

## 3. 更新包与发布流程

同一次构建生成同一个 Memivy 应用的两种分发文件，不增加另一个应用，也不要求用户安装两次：

| 文件 | 使用者与用途 |
| --- | --- |
| `.dmg` 与现有校验文件 | 用户首次安装，或更新失败时手动安装 |
| `.app.tar.gz` | 更新器下载的完整应用包 |
| `.app.tar.gz.sig` | 更新包签名；供更新器验证来源与完整性 |
| `latest.json` | 版本、更新说明、具体版本的下载地址与签名 |

发布顺序保持为：

1. 复用现有构建脚本，增加官方更新产物与版本清单的生成、检查。
2. 将 DMG、更新包、签名和清单放入同一个 GitHub Release 草稿。
3. 完成安装及真实旧版升级验收。
4. 正式发布并标记为最新稳定版，客户端才能发现更新。

更新包地址固定指向对应版本。已发布的标签和二进制不覆盖，修复通过新版本发布。更新文件需公开下载，客户端不嵌入 GitHub 私有访问令牌。

Tauri 更新签名私钥存入 CI Secrets，并另做安全备份；公钥随应用发布。私钥不进入仓库、应用包或日志。

## 4. 安装与数据保护

- 使用官方插件完成下载、更新签名校验及应用包替换，不自行编写安装器。
- 全量更新只替换应用包。资料库、模型配置和已下载模型保留在现有目录，不随更新重新下载模型。
- 复用现有双窗口草稿保存、退出协调和重启机制。两扇窗口确认保存成功后才能安装；失败则暂缓安装。
- 录音、转写或其他不能安全中断的操作尚未结束时，提示稍后更新。后台工作在安全边界停止接收新任务并退出，不设计复杂的自动接管。
- 外部 MCP 进程仍运行时，提示用户先断开或退出对应连接，暂缓安装，不强行结束其他应用的进程。
- 更新由 Rust 端统一协调，避免两个窗口重复执行。
- 断网、下载失败或签名不匹配时不进入安装，允许重试。不能将失败显示为更新成功。
- 安装目录不可写、从 DMG 运行等情况给出具体错误或安装指引。保留 DMG 手动安装作为退路，不承诺安装过程具备自动降级或断电恢复能力。

## 5. 数据库版本、迁移与备份

### 当前基础

目前正式数据库为 schema 1。现有代码支持新库初始化、版本校验及备份恢复，但没有 schema 1 → 2 → 3 的顺序迁移执行机制；恢复入口也要求数据库版本与当前程序一致。

### 本次要实现的最小能力

1. **版本检查。** 应用版本与数据库版本独立。结构没有变化的应用升级不迁移、不重复生成迁移备份。继续拒绝不属于 Memivy 或比当前程序更新的数据库，不重置用户资料库。
2. **迁移入口。** 新版应用启动时，在界面业务、后台任务和数据库写入开始前检查并执行必要迁移。在线更新与手动安装使用同一路径。
3. **独占与备份。** 复用现有跨进程访问协调，在迁移期间阻止并发写入。先用现有 SQLite 一致性备份能力保存并校验迁移前副本；备份失败则不迁移。副本放在资料库的恢复目录中，不包含模型密钥和模型权重。
4. **顺序迁移。** 保持已发布的 `migrations/memory/001_initial.sql` 不变，未来按顺序增加 schema 2、3 等迁移。用户跳过应用版本时，依次执行缺少的迁移。只用现有 Rust/SQLite 能力，不增加框架。
5. **事务与失败处理。** 将本次所需数据库变更和版本更新放在事务内，通过完整性检查后提交。失败时回滚事务、保留备份并停止正常业务启动，明确报告失败；不能用空库替代原库。测试中途失败或进程中断后的再次启动。
6. **旧版备份恢复。** 对支持的旧版备份，先在临时副本上迁移并校验，再衔接现有安全恢复流程。原备份保持不变，恢复前仍备份当前资料库。不支持的版本明确拒绝。
7. **旧进程保护。** 迁移期间 MCP 不得写入；迁移后，旧版进程遇到不兼容版本必须拒绝读写。

本次保持正式 schema 1，不虚构实际结构变更。用合成数据和测试迁移验证上述能力，未来增加真实迁移时仍需针对该次变更补充测试。

不实现数据库自动降级。新版已产生数据后，恢复旧备份可能丢失之后的内容，因此不能把恢复旧备份当作无损回滚；应用缺陷优先通过更高版本修复。

## 6. macOS 签名与权限边界

- 本次沿用现有 ad-hoc 签名和未公证分发，不把购买 Apple 开发者账号纳入实施前提。
- Tauri 更新签名负责验证更新包，不替代 Apple Developer ID 签名和公证。
- 已有未公证 Tauri 项目说明应用内更新不会重复触发首次下载的 Gatekeeper 提示，但这不是对所有 macOS 环境的保证，也不是“一次放行永久信任所有新版”。
- ad-hoc 签名不能可靠地维持跨版本代码身份，更新后麦克风可能需要重新授权。验收时明确检查，不承诺现有签名方式下授权永久保留。
- 不通过关闭系统安全保护或自动清除隔离标记来掩盖问题。若实际体验不能接受，再单独决定是否引入 Developer ID 签名与公证，不在本次静默扩大范围。

管理员安装授权、Gatekeeper 放行和麦克风授权是不同检查项，验收记录分别说明。

## 7. 验收与交付

### 更新链路

- 用真实的、带更新器的旧包升级到新包，验证检查、下载、签名校验、安装及重启。
- 验证无新版、网络失败、错误签名、安装权限不足时的反馈和重试。
- 验证两个窗口的草稿、记忆、设置及模型缓存保留。
- 验证录音、转写和外部 MCP 活跃时不会贸然安装。
- 验证更新后的启动、再次启动和麦克风使用，分别记录系统提示与权限状态。

### 数据库链路

- 验证同版本正常打开且不重复备份，未来版本及无关数据库被拒绝。
- 验证顺序迁移、跳版本迁移、迁移前备份及数据完整性。
- 验证备份失败不迁移，迁移失败或中断后不留下半迁移数据。
- 验证旧备份副本迁移、恢复失败保护，以及 MCP 并发与旧版本访问边界。
- 使用隔离合成数据运行相关 Rust 测试、现有核心回归和备份恢复检查，并进行独立数据安全审查。

开发验证遵守现有 Memivy Dev 身份、启动器及共享锁规则；正式身份的安装升级验收使用独立 macOS 测试账号或隔离测试环境。保护日常安装、生产资料库及其他任务的工作，不用开发模式替代正式升级验收。

实际实施和检查结果记录到现有 `DEVELOPMENT_PLAN.md`。未完成的原生验收明确列出，不把构建、包级模拟或其他项目的经验当作 Memivy 已通过验收。

现有不带更新器的旧版用户，需要手动安装一次带更新器的新版，之后才能在应用内更新。

## 8. 明确不做

后台定时检查、静默安装、强制更新、增量补丁、多发布通道、灰度推送、自建更新服务、CDN、更新统计、自动降级，以及额外平台支持。
